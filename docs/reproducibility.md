# Reproducibility

Two kinds of artefact, gated two different ways, for a reason that was measured
rather than assumed.

## Integer and string artefacts are gated by digest

Corpora are generated by seeded walks over grammars. Every operation is over
integers and strings — choosing, formatting, joining — with no floating point
anywhere, so the output is **bit-identical on every platform, forever**.

```bash
pifw check --plan main --corpus examples/corpus.jsonl.gz
```

re-derives the corpus from its plan and compares SHA-256 digests. CI runs it, so
a corpus edited by hand fails the build rather than silently changing every
number downstream.

Three details make that work:

**Gzip is stamped with `mtime=0`.** Without it the same corpus written twice has
different bytes and the committed digest cannot be checked at all.

**One seeded `Random` per bucket, not one per run.** With a single stream, adding
a family or nudging one weight shifts every draw after it and the entire corpus
changes. Per-bucket streams mean a change to the `markup` builder changes the
markup samples and nothing else, so a diff of the regenerated corpus shows what
was actually edited.

**Seeds are strings, not integers.** `Random(f"{seed}:attack:{family}")` — so two
buckets with adjacent integer seeds do not produce correlated streams.

## Float artefacts are gated on metrics, within a tolerance

Trained weights are **not** bit-identical across platforms, and asserting that
they are would produce a test that fails on somebody else's machine for reasons
nobody can act on.

This was measured in the previous project in this series rather than assumed:
1,344 of 55,872 weights differed between Windows and Linux, by up to 2.4e-14
relative, because BLAS accumulation order is a property of the build. The loss
was bit-identical; the weights were not.

So:

* the model's `config_digest` covers the **configuration** — the featuriser spec,
  the family list, the parameter count — all integers and strings;
* the weights are not digested, and no test asserts cross-platform weight
  equality;
* the model is gated on its **metrics**, against a recorded baseline, with a
  five-point tolerance.

`Model.load` checks `config_digest` and refuses a mismatch, because a weight
vector read against the wrong featuriser produces scores rather than errors.

## Why this model needs no random numbers at all

Logistic regression is convex. Weights start at zero, training is full-batch, and
there is no shuffle. So unlike a neural network there is no initialisation to
reproduce, and the previous project's discovery — that numpy's `standard_normal`
is **not** bit-reproducible across platforms, because its ziggurat tail branch
calls `log` and libm's `log` differs by one ULP between platforms, so exactly one
value in 32,768 differs — simply does not arise here.

That was a deliberate choice when picking the model, not a happy accident. The
cheapest fix for a whole class of reproducibility problem is a model that needs
no random numbers.

## The hash is specified, not implementation-defined

Features are hashed with BLAKE2b, not Python's `hash`.

`hash("ignore")` is salted per process by default. A model trained in one
interpreter and loaded in another would index different buckets and produce
different scores from the same weights. **Nothing crashes.** The accuracy just
quietly drops, in a way that reproduces on no machine and looks like a bad model
rather than a bad hash.

`tests/unit/test_model.py` pins a known digest value. If it ever changes, every
trained model in the wild indexes different buckets — which produces worse scores
rather than an error, so nothing else in the suite would notice.

## Training terminates on a criterion, not a budget

`max_iterations` is a ceiling, not a target. Training stops when no coordinate of
the gradient exceeds `tolerance`, and the model carries `converged` and
`iterations`.

The evaluation **refuses** to report a bypass rate for a fold whose model hit the
ceiling. This is not fastidiousness: the first version of this project ran a fixed
400 steps of plain gradient descent and produced a headline bypass rate of
**40.47%**; trained to convergence the same code gives **20.89%**. Both outputs
looked exactly like a measurement.

An absolute criterion on the gradient rather than a relative one on the loss,
because the loss flattens long before the weights stop moving — a loss-change
test declares victory early, and does it most confidently on the runs that need
the most iterations.

## What is *not* reproducible, and is not claimed to be

* **Wall-clock timings.** The performance assertions in the test suite are
  tripwires for quadratic behaviour with generous budgets, not benchmarks.
* **Weights, bit for bit, across platforms.** See above.
* **Anything about a real model's behaviour.** This package never calls one.

## Checking a fresh clone

```bash
git clone https://github.com/kogunlowo123/prompt-injection-firewall
cd prompt-injection-firewall
uv sync --group dev --group docs
python tasks.py all
```

`python tasks.py all` runs what CI runs: lint, types, the full suite with the
coverage gate, the corpus digest check, the twelve-fold evaluation against the
committed baseline, the gates' own negative controls, every example, and the
documentation build.
